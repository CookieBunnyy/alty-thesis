# Deploying ALTY

| Part | Where | Config |
|---|---|---|
| Website (`website-side/frontend`) | Vercel | `vercel.json`, env var `VITE_API_URL` |
| Main Alty API (`desktop-side/backend`) | Render | `render.yaml` (Blueprint) |
| Chat recommender (`website-side/backend`) | Render (already deployed) | — |
| Central data, files | Supabase | existing project |

## Secrets never go in git

`.env` files are gitignored and have never been committed. On Render, every
secret is entered in the dashboard (**Environment** tab) and stored encrypted
there; `render.yaml` only *names* them (`sync: false`). The backend reads
them as environment variables, exactly like it reads `.env` locally.

Never put `SUPABASE_SERVICE_ROLE_KEY`, `TOMTOM_API_KEY`, `SECRET_KEY` or a
database password in a `VITE_*` variable: anything prefixed `VITE_` is built
into the public website.

## 1. A database for the API

The API needs its own PostgreSQL that Render can reach (`localhost` doesn't
exist on Render). **Don't point it at your existing Supabase `public`
schema**: the API's migrations create `agents`, `clients` and `transactions`
tables, which already exist there with a different structure. Use one of:

- **Render PostgreSQL** (New → Postgres). Use its *Internal Database URL*.
- **A second Supabase project** (free tier allows two). Use the
  *Session pooler* connection string (Project Settings → Database); the
  direct connection is IPv6-only and Render can't reach it.

Either `postgres://…` or `postgresql://…` works — the backend converts it.

To move your existing local data there (optional):

```bash
pg_dump --no-owner --no-acl -Fc "postgresql://postgres:PASSWORD@localhost:5432/abellar" -f alty.dump
pg_restore --no-owner --no-acl -d "CLOUD_DATABASE_URL" alty.dump
```

## 2. Deploy the API on Render

1. Push this repo to GitHub.
2. Render → **New → Blueprint** → choose the repo. It reads `render.yaml`.
3. Fill in the prompted values:

   | Key | Value |
   |---|---|
   | `DATABASE_URL` | from step 1 |
   | `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | same as your local `.env` |
   | `TOMTOM_API_KEY` | your key (empty = no live traffic) |
   | `INITIAL_ADMIN_PASSWORD` | creates the first admin on an empty database |
   | `CORS_ORIGINS` | your Vercel URL(s), comma-separated, e.g. `https://alty.vercel.app` |

   `SECRET_KEY` is generated by Render automatically.
4. Deploy. Migrations run on every start (`alembic upgrade head`).
   Check `https://<your-service>.onrender.com/health` → `{"status":"ok"}`.

The free plan sleeps after 15 minutes idle; the first request then takes
~30–60 s (the website shows its loading bar meanwhile).

## 3. Point the website at it (Vercel)

Vercel → Project → **Settings → Environment Variables**:

- `VITE_API_URL` = `https://<your-service>.onrender.com`
- `VITE_CHAT_API_URL` = your chat service URL (optional; has a default)

Then **Redeploy** — Vite bakes these in at build time, so changing them
requires a new build. `vercel.json` makes page links like `/properties`
work on refresh.

### Staff password recovery and sign-in protection (Render → Environment)

Secrets go only in Render's Environment tab (never in `VITE_*` variables):

| Variable | Value |
| --- | --- |
| `STAFF_APP_URL` | the Management System's address, e.g. `https://alty-msa.vercel.app` — reset links are built from this, never from the request |
| `EMAIL_PROVIDER` | `resend` (HTTPS API; Render's free plan blocks SMTP ports) |
| `RESEND_API_KEY` | Resend → **API Keys** → create one with *Sending access* (secret) |
| `EMAIL_FROM` | an address on your domain verified in Resend, e.g. `no-reply@yourdomain.com` |
| `CLIENT_IP_HEADER` | `cf-connecting-ip` (Render runs behind Cloudflare; `X-Forwarded-For` can be forged) |
| `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY` | optional Cloudflare Turnstile keys (dashboard → Turnstile → add the Vercel domains). The site key is public; the secret is not |

**Resend setup:** Resend → **Domains** → add your domain and create the DNS
records it shows (SPF/DKIM) at your domain registrar, then wait for
"Verified". Until a domain is verified Resend only sends from
`onboarding@resend.dev` *to your own Resend account address*, so reset emails
to other staff would be refused.

Optional tuning: `PASSWORD_RESET_TTL_MINUTES` (15–30, default 20),
`LOGIN_COOLDOWN_STEPS` (default `5:60,10:300,15:900` = failures:seconds),
`LOGIN_CAPTCHA_AFTER_FAILURES` (3), `LOGIN_MAX_ATTEMPTS_PER_IP` (60 per 15 min),
`PASSWORD_RESET_PER_EMAIL_PER_HOUR` (3), `PASSWORD_RESET_MIN_EMAIL_INTERVAL_SECONDS` (120),
`PASSWORD_RESET_PER_IP_PER_HOUR` (10).

After deploying, sign in as the Administrator and open
`https://<api>/api/v1/system/security-check`: `detected_client_ip` must be your
own public IP (not a Render/Cloudflare address), and it shows whether email,
the reset link address, Turnstile and CORS are configured (no secret values).
Every staff member needs an **email** (Users & Access → edit) to use
"Forgot password?".

### Separate app for the Management System (Alty MSA)

The public site and the Management System install as two separate apps
only when they are on different domains (an installed app covers every page
under its address). Both domains point at the same Vercel project:

1. Vercel → Project → **Settings → Domains** → **Add** a second domain, e.g.
   `alty-msa.vercel.app` (any free `*.vercel.app` name, or your own domain).
2. **Environment Variables**:
   - `VITE_SITE_URL` = `https://alty-thesis.vercel.app` (the public site)
   - `VITE_MSA_URL` = `https://alty-msa.vercel.app` (the new domain)
3. Render → API service → **Environment** → add the new domain to
   `CORS_ORIGINS` (comma-separated), so the Management System can call the API.
4. **Redeploy** the website.

`/manage` on the public domain then moves to the MSA domain, and public pages
opened on the MSA domain move back. Staff sign in once on the new domain.

## 4. Point the desktop app at it

Desktop → **Settings → API server URL** = the Render URL → Save → restart.
Then the desktop and the website share the same data.
